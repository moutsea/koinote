## 上线导入

仓库文件存入专用私有 R2 桶 `koinote-agent-repositories`，服务器数据库仅保存元数据、权限和文件引用。先完成 [R2 配置与迁移](../../docs/AGENT_REPOSITORY_STORAGE.md) 并验证存储访问，再执行这 100 个仓库的导入。系统仓库没有个人所有者，管理员身份仅用于操作授权和审计。

先预览，不访问服务、不写入：

```sh
python3 scripts/seed_agent_repositories.py
```

这批公共内容直接属于系统目录（`is_system=true`、`user_id=NULL`），不计入任何管理员的「我的空间」、个人仓库名额、容量或 MCP 私有仓库访问范围。系统目录目前有独立的 1,000 个仓库保护上限；每次 GitHub 导入仍受现有文件、大小、敏感内容和速率限制。管理员无需付费资格或开启个人云端同步，任意管理员都可在「管理后台 → 系统仓库」查看、撤回和重新公开。系统收录标识不替换 GitHub 原作者、来源链接和许可证。普通用户自己导入或 Fork 的副本仍是个人仓库。

100 个新仓库预计需要约 300 次 GitHub API 请求，超过 [GitHub 匿名访问每小时 60 次的限制](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。批量导入前，应在「管理后台 → 系统仓库」配置只读 GitHub Token；脚本不会接收或另存 GitHub Token。Koinote 每用户每分钟最多导入 5 个仓库、写入 20 次，脚本按 `Retry-After` 等待重试；完整首次导入和发布通常需要二十多分钟。

```sh
python3 scripts/seed_agent_repositories.py \
  --apply \
  --base-url https://your-koinote.example \
  --admin-email curator@example.com \
  --cookie-file /secure/path/koinote-cookie
```

`--admin-email` 必须与当前登录账号一致。脚本先验证系统目录接口，再通过 `/api/admin/agent-repositories/import/github` 将全部仓库导入为尚未公开的系统仓库并核对内容，然后逐个公开，最后验证匿名访问；成功后会打印各自的 `/repositories/{id}` 链接，可在「Skills/Agent Hub」浏览。首次全量发布按清单逆序执行，同一 Koi 安装兼容分组内按发布时间倒序展示，使各批次保留清单顺序；重跑不会刷新已有发布时间。同一分组内，新发布条目显示在较早发布条目前方。创建失败时不公开后续内容；公开阶段失败可能已有部分仓库公开，可凭输出确认状态。固定导入 ID 在系统目录内全局去重，另一位管理员可以接续同一次导入。

固定 `requestId` 使中断重跑复用原仓库；已经公开且内容一致的仓库不会重复发布。若有人编辑过内容，脚本会停止，不覆盖修改。`--apply` 会公开尚未公开的原始副本，包括先前手动撤回的副本，因此撤回后不要再对该条目运行 `--apply`。需要换一批内容时应另建清单，保留旧清单与请求 ID 的对应关系。

可以通过重复 `--only owner/repo` 分批导入或仅重试指定仓库；筛选不会更换 `requestId`，也不会触碰未选中的条目：

```sh
python3 scripts/seed_agent_repositories.py \
  --only cloudflare/skills --only google-gemini/gemini-skills
```

上述命令仍只预览，实际执行时附加前文的 `--apply`、站点和账号凭据参数。撤回某条目后，只选择仍计划公开的仓库执行，避免将它再次公开。

撤回和重新发布在 Admin 的系统仓库管理中完成。公开显示的作者仍是原 GitHub 作者。清单导入脚本仅用于首次收录；后续更新使用下面的每日任务，不能用固定初始版本的导入清单覆盖新版本。

## 按需同步 GitHub 来源

Skills/Agent Hub 的 GitHub 来源仓库详情提供「从 GitHub 同步」按钮，检查当前默认分支并更新到最新提交。Fork 或 Clone（下载 ZIP、同步到本机或生成 Agent 安装指令）前也会检查上游，使用更新后的同一份文件快照；传输过程中仍固定版本，避免混用不同提交的文件。

页面统一通过 `POST /api/agent/repositories/{id}/sync?recheck=false` 准备一次最新快照，由服务端根据当前记录决定更新或跳过，不使用页面缓存的上游标记判断；再用 `refresh:false` 提交 Fork/Clone，避免服务端重复请求 GitHub；省略该字段的 API 调用仍默认检查上游。公开快照包含独立于文件版本的 `publicationId`（精确到微秒的发布时间），页面提交 `expectedRevision` 与 `expectedPublication`，并在操作事务内一起校验。同一 revision 重新发布或改变许可证也会使旧准备请求冲突；已完成的 Fork 仍返回原来的私人副本。公开清单与文件请求通过 `publication` 查询参数固定同一次发布，下载前后复核及 Agent 安装指令也受此约束。历史 API 调用未提供发布标识时保留原有版本校验。准备请求与手动同步使用独立限流额度，保持 Clone 的原有操作额度。

系统收录因许可证变化、许可证文件待审核或来源身份不符而拒绝更新时，准备操作返回仍有效的已保存公开快照，以及 `skipped` 和具体原因，允许继续 Fork/Clone；不会采用被拒绝的新内容。手动同步仍返回原来的错误供维护者处理。已撤回或删除的仓库不能通过这一回退重新使用。

发布时选择的许可证与上游许可证不同，但上游许可证本身未变化时，单独返回 `publication_license_mismatch`，不提示为「上游许可证已变化」。同样保留当前公开版本供 Fork/Clone，等待维护者核对发布许可证；每日维护会将此情况列为需要人工处理。

Clone 的相同请求 ID 重试不会重复计数；若该请求固定的公开版本已被替换，服务返回 `409 revision_conflict`，客户端重新读取当前快照，下一次操作使用新的请求 ID。已归档来源和没有 GitHub 来源的仓库同样读取当前公开版本；开始传输后仍固定该快照。Fork 在上游刷新返回后重新检查已完成请求，同一请求的并发重试返回原来的个人副本，不因上游版本变化或临时失败转成新的 Fork。

手动同步不会清除结果尚未确认的 Fork/Clone 请求 ID，即使同步已更新公开版本。再次操作时，已完成的 Fork 返回原副本；Clone 由服务端检查原快照是否仍然有效，确认冲突后才重新准备新请求，避免丢失响应后重复创建或计数。

GitHub 明确标记为已归档、已禁用，或仓库元数据接口确认来源不可访问、已转为私有时，保留最后可用的文件并展示上游状态，不下载新归档。已标记的仓库仍可 Fork/Clone；符合更新条件的仓库可点击「重新检查 GitHub」检查恢复状态，上游恢复后清除标记。个人 Fork、已编辑或关闭云端同步的副本不请求上游，详情返回 `syncDisabledReason` 并停用同步按钮、显示原因；个人 Fork 继承的状态只描述 Fork 时保存的来源，不承诺重新检查。限流、凭据失效、网络故障、GitHub 5xx，以及提交或归档下载失败都不是废弃依据，不会误标。没有使用长期未提交等启发式规则。

同步沿用数字仓库 ID、许可证、敏感内容、大小与归档结构检查，不执行上游代码。系统收录保留人工整理的名称、简介和分类；直接导入的个人仓库仅在已启用云端同步、没有个人文件修改、没有未公开修改时更新，并继续受个人配额约束。已有个人 Fork 和编辑过的副本不会被覆盖。Fork 确认说明新操作会检查并复制最新可用的公开版本，可能与当前预览不同；未确认结果的重试仍使用原请求和快照。许可证变更、许可证文件待审核、来源身份不符，以及云端同步关闭或缺少访问授权时，页面显示各自的处理原因。撤回的仓库不会因同步重新公开。

个人仓库的所有刷新写入在事务提交前持有所有者锁并再次确认同步开关，修改同步设置也使用同一把锁。若关闭同步已在下载期间完成，本次刷新保留原有私人文件和公开快照；来源信息更新或废弃标记写入也不能越过已完成的关闭操作。

新 Fork 同样在目标用户的所有者锁内、完成幂等回放检查后复核同步开关。若用户已在准备期间关闭同步，返回 `403 agent_workspace_disabled`，不新增私人仓库、文件或容量占用。页面刷新同步设置并提示重新启用，避免误报为容量不足；重新启用后可以安全重试原请求。

无需访问上游的个人 Fork、已编辑副本或已关闭云端同步的副本，使用同一套资格判断先跳过更新，再决定是否需要凭据和 GitHub 数字 ID。即使保存的 Token 因密钥轮换无法解密，或历史个人来源缺少仓库 ID，仍可读取、Fork 和 Clone 已公开的快照；真正需要访问上游的仓库继续严格校验身份，不从当前 URL 自动认领缺失的 ID。

公开操作不要求管理员身份或会员资格；已登录用户使用自己的已配置 GitHub Token，未配置时使用 GitHub 匿名请求额度，不借用其他账号的凭据。Fork 自身原有的会员、云端同步与空间限制不变。

所有系统收录（含首次导入）及已发布个人仓库的新归档均按固定 SHA **匿名下载**，直接读取 `codeload.github.com` 的无签名 ZIP 地址，不占用共享匿名 REST API 额度；元数据和提交查询仍可使用访问者自己的 Token。归档请求不携带 Token 或 Cookie，也不跟随重定向到签名下载地址，证明将要公开的具体内容可公开读取。即使仓库在元数据或提交检查后转为私有，具有读取权限的 Token 也不能将私有新内容写入公开快照；匿名归档读取失败时保留原快照，不凭下载失败永久标记来源。未发布的个人仓库仍可使用所有者 Token 更新私有来源。

归档服务的普通 `401` / `403` 归类为下载失败，提示稍后重试，不误报 Token 失效，也不重复整轮匿名解析；明确的限流响应仍按限流处理。真正的 GitHub API 认证错误保留原有 Token 回退及每日任务的停止规则。

已保存 Token 因密钥轮换等原因无法解密时，交互式刷新也尝试匿名读取公开来源。成功响应保留实际更新状态，并附带 `warningCode: github_credential_unavailable`；同步、Fork 和 Clone 页面提示本次使用公开访问及重新保存凭据的处理方式。匿名元数据也不可访问时仍返回凭据不可用错误，不据此永久标记来源。数据库错误不走这一回退，限流和网络错误仍按实际原因返回。

Fork 准备阶段的凭据异常或许可证审核提醒随成功结果暂存在当前会话的查询缓存中，按账号和新私人仓库 ID 隔离。跳转到私人仓库详情后继续显示，可手动关闭；不会随跳转立即丢失，也不会出现在其他账号或仓库中。缓存保存结果代码，切换语言时重新翻译提醒。

交互式刷新与 GitHub 导入共用并发额度，同一后端进程最多同时处理两个导入或刷新；同仓库、相同 GitHub 访问上下文的重叠刷新复用进行中的任务，不重复下载归档。并发已满时返回可重试错误，不继续占用下载和解压资源。每位访问者仍单独读取自己的收藏状态，不共享可变的用户视图。

交互式刷新遇到已保存 Token 失效或被拒绝访问时，会尝试匿名访问公开来源；匿名也不可访问时保留凭据错误，不因这次回退将仓库误标为不可用。GitHub 限流不触发匿名重试，每日维护任务的凭据失效处理也保持不变。

交互式刷新和每日维护的认证元数据请求返回 `404`、`410` 或 `451` 时，先匿名核实：公开可访问则继续使用匿名请求完成身份、许可证和内容检查；匿名也确认不可访问后才标记上游状态。匿名核实遇到限流、网络故障或 5xx 时保留原状态，不把访问者的权限问题当成仓库废弃。

## 每日更新系统收录

`.github/workflows/sync-system-agent-repositories.yml` 每天 UTC 20:17（北京时间次日 04:17）运行。任务读取数据库中全部存活的系统仓库，而非固定的 100 条初始清单，以后新增的系统收录也会自动加入。没有 GitHub 来源的条目会记录为跳过；个人仓库和用户 Fork 不在更新范围内。

合入 `main` 并完成包含 `/app/koinote-repository-sync` 的后端镜像及迁移（截至 `0093_agent_repository_sync_safety.sql`）部署后，定时任务即可工作。若第一次定时触发早于后端部署完成，会因缺少命令而失败，部署后可手动重试。任务复用已有的 `VPS_HOST`、`VPS_SSH_KEY`、`VPS_HOST_KEY`，使用当次工作流自带的短期 `github.token` 读取公开 GitHub 仓库，不需要管理员 Cookie、个人 GitHub Token 或新的长期密钥。数据库和 R2 凭据只在现有后端容器内使用。

更新规则：

- 跟踪 GitHub **当前默认分支**，而不是初次导入固定的 SHA；先解析提交 SHA，有变化才按该 SHA 下载归档。提交未变化时不下载、不上传、不增加版本或刷新发布时间；若 GitHub 数字身份相同但仓库改名或转移，仍更新内部及已有公开快照中的来源地址和作者信息，保留原提交、引用和个人 Fork。预览只报告该变更；正式更新记入系统审计，结果为 `updated` / `source_updated`，重复运行返回 `unchanged`。
- 更新前核对 GitHub 数字 ID；同一个仓库改名或转移后仍可更新，同名地址被另一个仓库复用时拒绝更新，即使 SHA 相同也不能绕过检查。迁移 `0093` 用原始采集时的数字 ID 补齐首批 100 条匹配的系统记录；匹配导入 ID、URL 和 SHA，保留已有身份。其他旧记录缺少数字 ID 时返回 `repository_identity_mismatch`，须核实来源后处理，不根据当前 URL 自动认领身份。
- 保留 Koinote 仓库 ID、公开链接、人工整理的名称、简介和分类、Star/Clone 记录及用户 Fork；更新 GitHub 来源和提交信息，归档内的许可证原样保留。只上传新的内容哈希，复用已有 R2 文件。
- 文件、来源、版本、历史、公开快照与系统审计在同一事务内更新。公开条目同步到新版本；未公开或已撤回的条目仅更新内部文件，不会重新公开。下载期间发生管理员撤回、重新发布或版本修改时，本条更新取消，保留管理员操作。
- 凭据扫描、敏感路径、单文件 5 MiB、整库 64 MiB、5,000 文件及归档结构校验继续生效。自动更新与首次自动收录共用 MIT / Apache-2.0 / ISC 的许可证文件检查，核对根许可证、嵌套许可证与 NOTICE；缺失、无法识别或包含已识别限制时返回 `license_review_required`，交由人工核对。仅根 SPDX 标识不变不足以放行。来源不可访问、变为私有、许可证标识改变或变为未指定、扫描失败、R2 写入失败时保留原来的完整快照。
- 每日更新同样识别并持久化已归档、禁用、不可访问或转为私有的上游状态，保留最后可用快照并计入 `skipped`；归档或禁用时不解析提交、不下载归档。预览仅报告，不写标记。GitHub 数字 ID 不匹配时仍拒绝认领新仓库，不会以废弃标记绕过身份校验。
- 每条独立处理，普通失败不阻止其他条目；单仓库拒绝访问（普通 HTTP 403，`github_access_denied`）也继续处理后面的仓库。凭据失效（HTTP 401，`github_credentials_invalid`）、GitHub 限流（HTTP 429 或带限流响应头的 403）或任务中断则停止余下部分。正式全量运行逐条持久化进度，下次手动或定时全量运行从中断条目继续，不再花费请求额度重复检查已完成的前半部分；完成余下部分后清零进度，下一轮重新遍历全部。普通单条失败在下一轮完整遍历时重试。删除已完成条目不丢失进度。预览始终检查全量，单仓库重试只处理指定条目，两者都不改变全量进度。
- 已人工审核的补充许可证文本可按 GitHub 数字仓库 ID、精确路径、根 SPDX 和实际内容 SHA-256 复用审核结论。当前仅包括初始目录中 `vinvcn/mattpocock-skills-zh-CN` 的 `LICENSE.zh-CN.md`：该译本明确以根目录英文 MIT 许可证为准，审批记录见后端 `agent_repository_license.go`，摘要与 `catalog.json` 一致。译本内容改变、出现在其他路径或仓库时须重新审核；此例外不替代根许可证，也不跳过其他嵌套许可证、NOTICE 或敏感信息检查。首次自动收录与更新共用此规则。
- 日志逐条输出状态和汇总；存在可重试或瞬时失败时以非零状态结束，若失败条目全部属于 `needsAttention` 则以 0 退出。续跑汇总的 `resumedAfter` 表示起始位置，`total` 为本次剩余条目数；未完成时的 `resumeAfter` 表示下次接续的位置。任务不会自动等待 GitHub 额度恢复，确认恢复后可手动重跑，或等待下次定时接续；成功的条目不会重复改版。
- 汇总里的 `needsAttention` 是 `failed` 的子集，用于许可证变化、许可证文件需审核、来源身份不匹配等需要人工处理的失败。上游已归档、禁用、不可访问或转为私有属于有状态的跳过，不再算失败。当整轮失败的条目全部需要人工处理时，命令以 0 退出，在日志里保留逐条结果和汇总；只要有一条是限流、凭据、传输、R2 或中断等瞬时故障，仍以非零状态结束。GitHub API 的传输失败和 5xx 记为 `github_transient_error`；归档下载传输失败记为 `github_download_failed`，均不会误报成仓库不可用。
- 数据库锁防止重复任务同时更新。部署替换容器时可能中断任务；已完成事务保留，进行中的事务回滚，可从工作流手动重试。每次任务最多运行一小时。

在 GitHub Actions 选择 **Sync System Repositories → Run workflow** 可以手动运行。默认 `dry_run=true` 仅检查和预览，不改数据库或 R2；取消勾选才实际更新。`workspace_id` 留空处理全部，也可填写 Koinote 仓库数字 ID 单独重试。

维护人员也可在生产主机上运行同一个脚本。以下命令从已设置的环境变量读取 GitHub token，通过标准输入送入容器，不写进参数或文件：

```sh
cd /opt/koinote
# 预览全部系统仓库
printf '%s\n' "$GITHUB_TOKEN" | sh deploy/sync-system-agent-repositories.sh
# 实际更新全部系统仓库
printf '%s\n' "$GITHUB_TOKEN" | sh deploy/sync-system-agent-repositories.sh --apply
# 单独更新指定仓库
printf '%s\n' "$GITHUB_TOKEN" | sh deploy/sync-system-agent-repositories.sh --apply --workspace-id 42
```

GitHub 的定时工作流可能延迟；公开仓库连续 60 天没有活动时，GitHub 会自动停用定时任务，恢复后需在 Actions 重新启用。详见 [GitHub schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。

## GitHub 链接收录与云端安装

新增 GitHub 来源采用链接收录：Hub 只保存仓库介绍、GitHub 数字 ID、原作者、来源链接、收录时的提交与许可证标识，不复制仓库文件。管理员可在「系统仓库」输入公开 GitHub URL，收录后核对并发布。例如 `https://github.com/dontbesilent2025/dbskill` 可走此入口；链接收录不代表对云端使用或再分发作出统一授权承诺，实际使用仍以来源条款为准。

用户点击「安装到 Koi AI」时复用 GitHub 安装预览，读取来源当前所选分支的固定提交，逐项显示可安装技能与不兼容原因。确认后仅将选中的技能保存到本人云端私有技能库，不产生公共镜像，也不打包进客户端。已安装状态按 GitHub 数字仓库 ID 查询，后续更新仍需预览确认。

已有镜像仓库、初始 `catalog.json` 的固定版本导入与现有用户的已安装技能保持原有行为；本次不批量迁移或删除历史内容。链接条目不提供 Hub 文件浏览、Fork、Clone 或镜像同步，可以到原 GitHub 仓库查看文件；不会被后台镜像兼容性检查标成“已验证可安装”。原安装大小、敏感内容、权限、额度和确认规则继续生效。

## 清点与转换已托管镜像

在支持链接收录的后端、网页和桌面客户端发布后，可用同一维护命令清点历史系统镜像。默认仅预览；确认 GitHub 仍公开、数字仓库 ID 相同且默认分支仍可读取后才转换。404、私有、停用、网络故障、身份变化或已安装来源冲突均保留镜像，并输出原因。公开且已归档的来源仍可转链接。不会操作用户私人仓库，也不会重新发布已撤回条目。

```sh
printf '%s\n' "$GITHUB_TOKEN" | sh deploy/sync-system-agent-repositories.sh --convert-public-to-links
printf '%s\n' "$GITHUB_TOKEN" | sh deploy/sync-system-agent-repositories.sh --convert-public-to-links --apply
```

执行前保留数据库备份和预览清单。每个仓库单独事务提交，保留 Hub URL、分类、介绍、收藏和发布时间，清除系统镜像的当前文件及文件历史。已安装 Hub 技能只迁移更新来源，保留 ID、开关、私有文件、不可变版本和运行中任务的版本引用；遇到同账号已有相同 GitHub 技能时保留镜像并报告冲突。旧安装预览需重新打开确认，不会悄悄改用新来源。

物理 R2 对象不直接删除：Fork 和私有技能引用继续有效，失去引用的历史对象遵守现有 401 天备份恢复保留期，再交给正常清理任务回收。因此清理后镜像入口立即消失，物理存储不会同步下降。旧版本客户端不识别链接条目，须先发布对应客户端再执行批量转换；仅运行预览可用于上线前清点。

## 每日发现热门 Skills 仓库

`.github/workflows/discover-system-agent-repositories.yml` 每天北京时间 **05:37、09:37、13:37、17:37、21:37** 执行，与 04:17 的已有镜像更新任务错开。每天最多新增 **20 个**公开 Skills 仓库链接，优先写作、知识管理与研究；保留每日至多 20 个、最低 100 Stars 和系统目录 1,000 个存活条目的上限。新增条目不占个人仓库或存储配额，明确用途归入「写作与内容」或「研究与知识」。

- 继续使用 GitHub 官方仓库搜索及原有定向关键词，筛选公开、非 Fork、未归档、未禁用的来源。通用搜索每组最多 300 条，定向搜索每组最多 200 条，先处理写作或研究知识用途，同组按 Star 数降序。正式收录补至当天名额或候选耗尽，预览最多检查 100 个未收录候选。
- 解析默认分支的固定提交，只读取公开文件树确认存在 `SKILL.md`，不下载归档或保存文件内容。文件树不完整且未找到技能时跳过，不宣称整库兼容；实际技能内容、大小和能力兼容性由用户主动安装时校验。
- 链接收录不再使用镜像再分发的 MIT / Apache-2.0 / ISC 筛选条件。此前因许可证或 Koi 预览限制进入冷却的候选可重新按链接模式检查；已有镜像更新继续沿用原来的许可与内容审查。
- 按 GitHub 数字 ID 和来源 URL 去重；已撤回、软删除的系统条目不重新上架。按北京时间自然日记账，删除条目不退还当天名额，元数据、公开目录、审计和每日记账在同一事务内提交。
- 不符合链接筛选条件的候选冷却 7 天；暂时性 GitHub 故障可重试。每个请求遇到 5xx、网络错误或 `incomplete_results` 时最多重试 3 次（间隔 0.5s、1s），限流及凭据失效停止本轮。当天名额用完后不再搜索或读取文件树，后续时段只补剩余名额。
- 候选不足时输出 `remaining` 和 `outcome=insufficient_eligible_candidates`。实际处理失败返回非零退出码，已成功条目和已记录冷却保留；同步任务会跳过链接条目，不将它们转换为镜像。

迁移 `0113` 将八个已核对用途的自动发掘来源从默认 Agent 分类整理到写作或研究知识分类。只处理仍公开、未删除且没有管理员操作记录的自动条目；已经人工分类、私人副本及撤回条目保持原样，不改变文件、版本和发布时间。

五个执行时段均由 GitHub Actions 调度，用于补偿个别时段漏跑，并非独立的备用调度器。GitHub 全局故障或工作流被停用时仍可能全部未触发；可通过下方命令手动补跑。补跑只填补当前北京时间自然日的剩余名额，不追补历史日期，也不会因删除仓库而重复增加当天额度。

部署包含 `0092_agent_repository_discovery.sql` 的后端及工作流后启用，凭据与每日更新任务相同。可在 Actions 的 **Discover Skills Repositories → Run workflow** 手动预览（默认 `dry_run=true`）或取消勾选后收录。预览会搜索并读取元数据和公开文件树，但不写数据库、冷却记录或 R2，也不消耗每日名额。

主机上也可复用同一个维护脚本：

```sh
cd /opt/koinote
```

`--discover` 不能与 `--workspace-id` 一起使用。不要把管理员凭证或个人 GitHub Token 写进工作流。GitHub 搜索的排序、分页和独立限流见 [官方 Search API 文档](https://docs.github.com/en/rest/search/search#search-repositories)。定时延迟、长期无活动停用和部署中断后的手动重试规则与上面的更新任务相同。
