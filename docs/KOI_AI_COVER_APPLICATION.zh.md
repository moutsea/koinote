# Koi AI 生图后的封面应用与上下文

本记录对应 2026-11-17 的代码修复、验证与发布。封面应用及上下文候选修正已随 Koinote 1.1.28 和独立 Agent 发布上线，最终版本与线上验收见末节；前文保留发布前的检查记录。通用理解问题尚未全部关闭。

| 问题与根因 | 实际改动及受影响链路 | 验证与剩余限制 |
| --- | --- | --- |
| 生图只能下载，不能用于文章封面：`generate_cover` 只保存私有会话附件，未提供文档封面操作 | 新增 `set_document_cover`，限定本用户、本会话已生成的图片，读取文章版本后转存至普通图床，并创建 `cover` 操作。`review`、`assist` 待审批；`full` 自动应用。沿用审批、取消、回执和撤销，前后端均识别封面改动 | 隔离 PostgreSQL + 实际 HTTP/MCP 路由覆盖两种入口及三档权限、重复请求、正文编辑期间审批/撤销、删除会话后保留封面。图片生成服务和 Worker/R2 使用 HTTP fixture；未实际调用生产图床 |
| “帮我设置”等追问丢失图片线索：历史只包含文本、文档操作和发布回执，没有产物描述；文章入口还替换了通用的追问连续性提示 | 原生会话提示和 `get_conversation` 加入产物 ID、任务归属、类型和大小；历史过长时支持按任务分页查询。补充文章入口的追问理解及封面复用指令，明确已有图片不因应用而重新生图 | 实际查询验证上轮图片进入下轮提示及历史工具；验证完整提示仍低于 20,000 UTF-16 单位、技能分页可继续。真实模型对“帮我设置”的意图判断尚未验收；结构性历史检查不能代表模型行为已验证 |
| 设置封面若直接使用私有附件链接，会在发布或删除会话后失效；撤销若恢复整篇快照，会覆盖正文新编辑 | Worker 使用共享内部令牌回调 Go 核验用户身份，沿用图片配额记账。转存期间不占用数据库连接；提交前重新核对取消、权限和版本。封面审批/撤销只核对和修改封面元数据，保留最新标题、正文、主题；迁移 `0123` 保留旧封面供预览和撤销使用，失败转存结果进入孤儿回收队列 | 单数据库连接下的转存/配额回调通过；存储不足、转存期间取消和用户改封面均不产生提案或额外生图扣费。实际数据库验证图片引用与删除会话后的保留；R2 对象写入、发布到外部渠道及生产回收未验收 |

客户端通过 `X-Koinote-Agent-Cover-Apply: 1` 声明支持封面审批。旧客户端仍能生成、下载图片，不会收到其无法展示的封面操作。设置、拒绝、撤销不调用生图服务、不增加生图 Credits；普通对话模型费用仍独立结算。封面和正文同时修改时，先应用封面，再重新读取版本提交正文修订。

本轮已实际运行：SPA/Worker TypeScript 检查、生产构建、Worker 图片回归 78 项、i18n 795 项、任务结果与进度回归、两个界面的生图/封面审批/差异预览/撤销浏览器回归。浏览器使用独立 headless Chromium、临时 profile 和随机调试端口。后端相关回归 179 项通过，两个需显式开启的付费真实模型用例跳过，未计入通过数；最终封面新增用例、完整提示预算及 CORS 又已定向复验通过。跨仓库内核契约的 3 个文件、25 项测试通过，模型返回使用 fixture，不视为真实模型验收。

界面改动参考 `modern-web-guidance` 的 accessibility 指引，复用带文字的原生审批按钮和现有差异弹窗，不引入新的交互控件。封面应用代码、迁移和本地回归已完成；生产部署、真实生图/图床与模型/宿主合并联调、渠道发布另行验收。发布需先让 Worker 支持内部图片转存，再更新数据库及后端，并更新前端/客户端。下述通用上下文候选修正还涉及共享 agent-gpt 服务，不随 Koinote 发布自动生效。

## Code review 后的封面比例修复

根因有两处：封面应用用四位小数构造 `W:1`，但前后端共用的比例格式最多接受两位小数，导致所有图片回退到 `2.35:1`；Koi 公众号发布又将比例固定为 `2.35:1`，没有保留文章的封面配置。修复前，实际数据库回归复现了 `940×529`、`560×560`、`324×940` 图片均保存为宽图比例，发布回归也实际捕获到上传的缩略图被处理成 `940×400`。

实际改动：应用封面时将图片的宽、高同时缩小 100 倍，以两位小数保存精确的像素比例，例如 `940×529` 保存为 `9.40:5.29`，符合现有校验及编辑器展示格式，无需放宽共用规则；公众号发布快照保留非默认封面比例，确认发布时使用该快照。旧发布快照缺少比例时保持原来的宽图行为，默认宽图快照仍省略新增字段，保留其原有摘要与重复发布判断。

受影响链路为生图 JPEG → 会话产物 → 封面提案 → 审批/直接应用 → 文档封面元数据 → 编辑器与普通发布，以及文档 → Koi 发布预览快照 → 确认 → 公众号缩略图上传。实际隔离 PostgreSQL 验证了横图、方图、竖图的比例持久化、审批、重复请求和撤销；发布测试通过实际 HTTP 处理器和图像处理代码，核对模拟微信接收端收到 `940×529` 的 16:9 图片，并继续验证确认、幂等和计费。

验证结果：相关后端 28 个顶层测试全部通过，无跳过；公众号封面传输 12 项、公众号草稿 70 项、网关流式回归及 `go vet ./internal/server` 通过。图片生成、图床和微信远端使用模拟响应，不视为真实 R2 或公众号生产验收。本次修复未部署；后续新设置的封面和新建发布预览使用修正后的比例，既有错误比例、待审批提案和旧发布快照不自动回填。通用上下文误澄清的未关闭状态见下文。

## Code review 后的历史发布去重修复

根因：新增 `coverRatio` 字段进入发布快照后，整份快照计算出的发布摘要发生变化；下游只按摘要匹配已发送、发送中和结果不确定的记录，因此同一篇未修改的非默认比例文章会绕过旧回执，再次发送并扣除 20 Credits。同一任务的旧待确认卡片重试也会被误判为其他版本，新旧两张卡片分别确认可能扣费两次。

实际改动：发布快照继续保存并使用真实封面比例，但计算去重摘要时使用比例字段为空的快照副本，保持上一版本的摘要格式。文章的任何封面改动均经共用 `updateDocumentTx` 推进 `revision`，且发布确认会核对该版本，因此真正的封面变更仍会形成新的发布身份。无需改写旧记录、迁移数据库或放宽确认权限。影响链路为文档版本 → 准备预览及同任务重试 → 持久化摘要 → 跨任务回执匹配 → 外部发送与计费；X、自定义渠道和 GEO 摘要等其余摘要字段保持原有规则。

实际验证：以旧版独立 JSON 结构和字段顺序在隔离 PostgreSQL 中构造旧快照及摘要，实际调用现有预览、确认、记账与图像处理代码；微信远端使用 HTTP 模拟。修复前复现了非默认比例失配后再次扣费，以及新旧卡片合计发送两次、扣除 40 Credits。修复后覆盖 `1:1`、`16:9`、`2.35:1` 与 `sent`、`sending`、`uncertain` 的九种组合，均不新增发送或扣费；旧待确认卡片同任务重试正常，新卡片发送后旧卡片复用同一回执，真正修改封面后的新版本仍正常发送并只扣费一次。相关 18 个顶层后端测试全部通过，无跳过，`go vet ./internal/server` 通过。

剩余限制：本次修改未部署，未执行真实公众号发送或生产验收；旧回执及卡片保持原有内容，不回填旧封面的裁切结果。通用上下文误澄清仍未关闭。

## 用户提供原文后的上下文诊断

已知片段是“根据文章内容帮我生成一张公众号封面图”→助手回复封面已生成，并附带换风格、换比例和旧选题等说明→“帮我设置”。按这段上下文，合理的有效目标是应用已生成的封面。缺少执行工具应作为能力限制说明，不能据此制造“技能设置或重新改图”等额外用户意图。

回放使用用户提供的文字，实际调用当前应用渠道的 `deepseek-v4.1-flash` 和真实 Agent 内核；Koinote 输入由隔离 PostgreSQL 导出。文章、前轮推断状态及读写工具回执是合成数据，更早的四个选题对话和原生产任务状态未取得。因此这是语义回放，不是原生产任务的完整重放，也不代表真实图片存储/文章写入的联合验收。

| 已证实的断点 | 实际改动及影响链路 | 验证与当前状态 |
| --- | --- | --- |
| 完整文字历史仍可能没有推进目标：旧配置回放把本轮目标保留为“生成封面”，未改成“设置已有封面” | 两个 Koinote 入口共用连续性说明，区分已完成步骤与新请求；封面规则不依赖“帮我设置”等短语白名单 | 该断点已在真实模型回放中观察到；不能仅凭历史传输测试认定理解正确 |
| 前置解释正确后，独立操作核对仍可能重判为歧义；把助手此前“不改文章内容”的描述当成用户限制 | Agent 的解释、操作核对、回复核对及执行上下文共用“指代上下文不等于授权”的规则。用户后续指令提供操作授权，助手回复只能帮助定位对象；不把助手的自述变成用户禁令 | 本地支持封面设置的配置通过真实模型回放：识别应用已有图片、调用设置工具一次、未重新生图、未改正文，最终回复核对通过 |
| 意图解释同时接收整份应用执行说明，产品功能、权限和缺失能力可能混入“用户想做什么”的判断 | `src/core/agent.ts` 的初次解释及澄清复核不再收到 `applicationContract`；原始对话、消息绑定资源及历史推断状态保留。执行、独立操作核对和回复核对仍保留完整应用规则，宿主权限/审批/来源校验未放宽 | 两项新增结构回归覆盖初次解释和澄清复核的隔离，并核对执行/审核约束仍在。此改动未单独解决所有误澄清，不能标记为通用理解已修复 |

本地 Agent 的 49 项意图/权限回归、TypeScript 检查，以及跨仓库 25 项内核契约回归通过。实际生效的 Agent 版本曾只读核对为 `23ecf95f-9a1c-4e50-85e6-c5e87540d207`，其三份核心源码与修改前本地源码一致。候选修正保存在 `deploy/agent-gpt/conversation-continuity.patch`，包含运行时代码和回归；没有部署该共享服务。

真实模型的四类普通多轮样例——助手建议干扰、仅建议不执行、显式切换目标、切换页面后继续原目标——通过。明确同时讨论封面和渠道两个未选方案的对照仍产生澄清，未执行操作。以上是有限样例，不是可靠性统计或所有上下文场景的证明。

**未关闭的反例**：刻意移除封面设置能力和图片产物事实后，模型仍会错误追问“帮我设置具体指什么”。单独强化连续性提示、隔离意图输入均未让这一对照稳定通过；对应澄清回执按失败记录，没有因测试进程曾返回成功就计为通过。进一步尝试“优先最近成果”的提示还导致真正有歧义的对照猜选了封面，因此该提示已经撤回，未包含在候选补丁中。另有一次回放在操作复核时返回附带额外文字的无效 JSON，协议仍按原有规则拒绝，没有放宽解析来掩盖失败。

诊断与回放证据保存在本机 `output/koi-context-2026-11-17/`。当前结论是：封面应用能力已补齐并有本地验证；用户指出的上下文理解问题也真实存在，但通用问题尚未全部解决、未通过生产验收，不应宣布彻底修复。
