# Koi AI 执行节点失活排查与恢复

## 当前状态

2026-11-20，最终执行器客户端已部署，`/health`、`/ready` 均恢复 200。
最终版本的真实写作链路和当前 Koi 会话 Skill 调用均通过验收；下文区分实际生产依赖、
隔离数据库和故障模拟的验证范围。

## 根因与影响范围

Koi AI 使用 `agent-gpt`。Worker 入口与模型渠道仍能响应，但唯一的 VPS 沙箱执行节点
`shared-01` 已失去控制连接。排查时其最后心跳记录为 2026-11-16 17:56:12 UTC，
执行器进程仍显示 active，却没有已建立的 TCP 连接；全局 `/ready` 返回 503。
因此普通模型回复可成功，需要沙箱的计算和工具任务没有可用执行节点。
这早于 2026-11-20 的 Koinote 部署 SSH 钥匙轮换。

客户端重连只依赖 WebSocket 的 `close` 事件。原有看门狗在同步超时后调用 `close()`
并清除 pending 标记；如果连接停在 CONNECTING/CLOSING 等非 OPEN 状态、没有完成关闭事件，
就不会再次重连。进程不退出，systemd 的 `Restart=on-failure` 也不会介入。
正常停止时，即使工作清理完毕，残留的原生 WebSocket 句柄仍可能阻止进程退出。

旧进程当时的具体 WebSocket 状态未被保留，不能断言它一定处于 CONNECTING 或 CLOSING。
这两条不能自愈的代码路径已通过子进程故障模拟复现；生产排查直接确认了连接失活、
进程仍在、没有运行中沙箱，以及恢复连接后就绪检查转为成功。

## 实际修复与共用链路

- 在执行器客户端增加单调时钟的连接进展检测。连接非 OPEN 且空闲超过 45 秒后，
  完成清理并以失败状态退出，由原有 systemd 监管重新启动。
- 有持有租约的任务时不因这个新看门狗强制重启，继续使用已有租约到期、取消和容器清理流程。
- 在确认清理完成后明确退出 CLI，避免卡住的 WebSocket 让正常停止或失败退出一直挂起。
- 正常断线时刷新重连宽限时间，保留原有退避重连；增加只含事件名、节点 ID、状态码的日志。
  节点凭据吊销、租约及防重复执行规则保持原有处理。
- 只更新 `204.44.93.247` 上 `/var/lib/agent-gpt/app/vps/agent.mjs`。
  共享 Worker 未重新发布，原运行版本 `e507c4d6-bc94-4491-82f6-81ca2bda7b7e` 的既有修复保留。

修复基于已部署归档和 VPS 实际文件 SHA，而非包含其他未发布改动的 Agent 工作区。
原客户端 SHA 为 `82d94d031cbc17534a77fb017fd3ed6ef9eae378b97549cef2422d4d30715c95`；
最终客户端 SHA 为 `117f396abb1d9bbfcd444afda6aee0f8dc3b744c4aa1e1fd37ac2bce875860ca`。

## 剩余边界

没有定位最初的网络断开事件，也没有在生产通过断网/冻结进程注入故障。
空闲节点的正常心跳间隔为 5 分钟，不能把几分钟未更新单独判为离线。
本轮未验证真实用户浏览器登录、公众号发布和新一轮生图；这些能力不能仅凭 `/ready` 200 标为通过。
测试结束后已移除临时 MCP 注册、停止回调隧道，并停止和删除隔离测试数据库。
